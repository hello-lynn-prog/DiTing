目标：把 BettaFish 的核心用户可见能力和研究行为，在 DiTing 的 TypeScript 后端内原生实现；由 dsh 负责 Agent loop、子 Agent 生命周期和工具调度。Python 源码只作为行为与数据契约的对照材料，不以 Python 子进程、HTTP 代理或“调用 BettaFish 服务”替代移植。

## 范围定义

“完整移植”指报告生成链路、研究引擎行为、研究状态、交互协作、数据统计、可视化报告和错误恢复能力均能在 TypeScript 实现中逐项验收。它不等同于把 Python 文件逐行翻译，也不表示已有六个角色名称或报告模板就代表功能已移植。DiTing 保留自己的证据归档、任务审批、费用预算、权限边界和审计机制；任何需要登录态的深采仍按用户批准的采集范围执行。

## 移植顺序

1. **引擎行为闭环**：先完成关键词优化、引擎内反思/查询循环、HOST 滚动信息流，避免只增加角色卡片而不改变实际研究行为。
2. **ReportEngine 交付等价**：实现类型安全的报告块 IR 和词云/SWOT/PEST/图表质检；保留 DiTing 的事实来源、统计底表与证据脚注机制。
3. **媒体与采集能力**：定义可审计的图片/视频素材适配器和内容抽取界面；需要外部模型或平台登录的能力显示配置/授权状态，不伪称已覆盖。
4. **验收与成本收敛**：用离线固定 fixture 完成确定性测试，再在用户明确预算下跑真实主题；记录真实输入输出 Token、样本数、调用次数、错误和最终报告。

## 需要真实业务条件的验收

- 微博与 B 站登录态样本：用户需在自己的浏览器登录并在 DiTing 的平台会话配置页面保存凭据；不要通过聊天粘贴 Cookie。
- 值守：需要用户给出关键词、升温门槛、通知策略和运行节奏。当前不擅自打开持续采集。
- 成本基线：需要用户确定总金额上限及 2–3 个代表主题；一次真实研究会调用收费模型。
- 远端 CI：本地 Git 仓库没有 remote；需要用户提供目标仓库地址后才能做远端验证。

## 许可与实现方式

移植目标是独立的 TypeScript 功能实现，不把 BettaFish Python 代码作为运行时依赖。复用源代码、提示词、模板或报告资产前须逐项核对其随附许可；当前项目的第三方来源边界见 `THIRD_PARTY_NOTICES.md`。此清单记录工程范围，不构成法律意见。
