# 舆情研判 Agent（YUQING）开发规划

> 2026-10-14 ｜ 依据：《舆情Agent控制台-仪表盘设计稿.html》（UI 契约）、《热点追踪与日报平台复刻方案》、《deepseek-harness-舆情Agent集成分析》
> 原则：**不复用 hotspot-agent 旧代码**，全新起仓；只继承三个已验证资产——`scripts/heat_state.py`（爆发判定）、采集守则语义（L1/L2 分级 + 审批）、五表设计的经验教训

## 一、技术底座（已定方向）

| 层 | 选型 | 说明 |
|---|---|---|
| Agent 运行时 | **DeepSeek Harness (dsh)** 候选底座，Go/No-Go spike 后锁定；No-Go 则自研薄 loop（400 行级） | guard=采集守则、subagent/plan=编队、mcp/skill=能力、schedule=值守、token-meter=成本、compaction=压缩，全部现成 |
| 多 Agent 编排 | **dsh-agent-teams 插件**（草案→确认→门禁→mailbox） | 拆解器/规划者/Worker/质疑者/核实员/撰稿员 = 一个 team profile |
| LLM | DeepSeek V4（Worker 打标/摘要）+ GLM-4.7（规划/质疑/核实/成稿） | OpenAI 兼容 function calling；路由表见原型 LLM 页 |
| 后端 | FastAPI 网关（自有 API + 转发 dsh api-gateway/session-query） | Python 存量能力经 MCP 桥挂入 dsh |
| 前端 | Vue3 + Vite + Naive UI，图表 ECharts/G6 | 原型 HTML = 高保真设计稿与验收标准 |
| 存储 | SQLite 起步（十张表，见 §四），Langfuse 自托管（观测） | 单机部署，PostgreSQL 预留 |

## 二、模块 × 开源复用对照（核心部分）

### A 线：发现与采集（热榜/日报的数据面）
| 任务 | 沿用项目 | 接法 |
|---|---|---|
| 多平台热榜聚合（60 源） | [newsnow](https://github.com/newsnext/newsnow) 22k · [DailyHotApi](https://github.com/imsyy/DailyHotApi) 4.1k | 各自部署，统一拉取落 `snapshots`；newsnow 失败返旧缓存模式照抄 |
| 关键词命中/增量推送逻辑 | [TrendRadar](https://github.com/sansan0/TrendRadar) 62.8k | 两个文件当库用：`crawler/fetcher.py`（拉取+域名校验+重试）、`core/frequency.py`（关键词 DSL）；9 渠道 `senders.py` 直接抄 |
| 长尾源（法广/少数派等） | [RSSHub](https://github.com/DIYgod/RSSHub) ~30k | 路由查询，feedparser 接入 |
| 爆发/回落判定 | **自研 `heat_state.py`**（已写完） | 环比×共振×绝对分三条件；老议题环比、新词走绝对分+共振 |
| L1 追赶式正文采集 | [dataabc/weibo-search](https://github.com/dataabc/weibo-search) 2.3k + Jina Reader | 命中即跟抓正文/互动数（无浏览器低风险）；Jina 走 MCP |
| L2 深挖（评论/帖文） | [MediaCrawler](https://github.com/NanmiCoder/MediaCrawler) 66.6k | ⚠️ 非商用协议：**独立进程运行、只读其落库数据**，代码不混入本仓；触发走审批 |
| 源管理（开关/健康度） | newsnow 自适应间隔模式 | 源注册表 CRUD + 探活，UI=定制中心 |

### B 线：研判（多 Agent + 链路 + 信号）
| 任务 | 沿用项目 | 接法 |
|---|---|---|
| 团队编排/草案/质量门禁 | [dsh-agent-teams](https://github.com/NanmiCoder/dsh-agent-teams)（MediaCrawler 作者） | 队长出研判草案→人工确认→成员按依赖执行；门禁顺序改为"取证→核实→质疑→成稿" |
| 辩论机制 prompt 组织 | [TradingAgents](https://github.com/TauricResearch/TradingAgents) | 多空辩论的角色 prompt 与消息传递范式，移植到质疑者 |
| 证据归档（URL→正文+时间戳） | [Firecrawl](https://github.com/firecrawl/firecrawl) / jina-reader MCP | `evidence.archive` 工具的实现；自带 MCP |
| 权威检索核查 | Tavily MCP | verifier 的 `search.web` 工具 |
| 研判链路 | **自研**（nodes/edges 两表） | 无现成舆情专用实现——这是差异化，agent-teams 任务板数据只作调度，展示层从链路表投影 |
| 信号打标 | snownlp（轻量）/ BettFish 微调模型集 + DeepSeek 复核 | 低置信自动转 LLM 复核队列 |

## 三、团队编成（team profile 即配置）

| 成员 | 模型 | 工具集 | 门禁位 |
|---|---|---|---|
| 主 Agent mainagent | GLM-4.7 | 全部（唯一用户入口） | — |
| 议题拆解器 goals | GLM-4.7 | 快照/历史事件库 | — |
| 规划者 planner | GLM-4.7 | 链路读写/全库检索 | — |
| Worker ×N | DeepSeek V4 | 采集/检索/打标/SQL只读 | — |
| 核实员 verifier | GLM-4.7 | evidence.archive / jina / tavily | 验证 |
| 质疑者 advocate | GLM-4.7 | 链路读写/检索 | 审查 |
| 撰稿员 reporter | GLM-4.7 | 链路只读/模板 | 人工审核后发布 |
| 值守 sentinel（cron） | DeepSeek V4 | 快照/关键词/推送（只读+通知） | — |

调度原则：值守巡检单 Agent；只有议题升级"研判中"才拉团队（token 成本纪律）。

## 四、数据模型（SQLite 十表）

```
sources(源注册表)      id,name,category,kind,url,interval,enabled,last_ok_at
snapshots(热榜快照)    ts,source,rank,title,url,heat
news_items(L1 正文)    url PK,title,body,author,pub_ts,first_seen,last_seen,likes,comments,brand/topic_ids
topics(议题)           id,name,kind(event|brand),goal,status(值守|研判|暂停|结题),keywords_json
signals(信号)          id,topic_id,level(高|中|关注),title,summary,evidence_ids,created_at
evidence(证据库)       id,url,archived_body,fetch_ts,quote,topic_id
chain_nodes / chain_edges   链路节点与边（type: root|hint|goal|intent|fact|signal）
daily_heat             date,topic_id,score,state(爆发|升温|持平|回落)
reports                id,kind(daily|event|brand),category,date,title,body_json,tags,model,tokens,status
usage_log / approvals  agent_id,tokens_in,out,cache,cost / 审批流
```

## 五、里程碑

| 阶段 | 内容 | 验收 |
|---|---|---|
| **M0 spike（1 周）** | dsh 跑通+agent-teams 插件安装+写一个最小舆情工具插件（heat_state 包装）+guard 审批链路 | 插件成本可控=Go；否则自研薄 loop+抄 guard/compaction/schedule 设计 |
| **M1 发现层（2 周）** | newsnow/DailyHotApi 部署、60 源接入、snapshots 落库、heat_state 判定、TrendRadar 式关键词推送 | 六分类真数据榜卡；一次真实命中→飞书预警 |
| **M2 研判层（2-3 周）** | team profile 六角色、链路两表+页面、信号产出、verifier/advocate 门禁跑通、采集守则+审批 | 一次真实事件端到端：命中→立题→团队研判→存疑打回→结题 |
| **M3 交付层（2 周）** | reporter 六段日报、详情页/RSS/归档、品牌监测（阵营卡+对比+竞品简报）、PDF 导出 | 每日 06:30 自动日报；一份带证据链的事件报告 |
| **M4 打磨（持续）** | 登录/套餐/Token 余量、Langfuse 成本树入仪表盘、M2 深挖（MediaCrawler 独立进程）、60→150 源运营 | 对客户可售演示 |

## 六、风险清单

1. dsh 开发者预览破坏性变更 → 锁版本，聚合器/插件隔防腐层
2. MediaCrawler 非商用许可 → 只独立进程+读库，代码零混入；商用深度集成需 Pro 授权
3. 上游源失效 → 每源探活+隐藏降级（newsnow 模式），单源挂≠系统挂
4. L1/L2 采集合规 → 登录态采集一律守则+审批；PII 脱敏常开；只抓公开信息
5. token 成本失控 → 值守单 Agent、研判才拉团队；构成拆解面板盯"工具结果占比"，超 60% 开修剪
6. 链路被任务板数据绑架 → 链路表是唯一事实源，任务板只是调度视图

## 七、建议仓结构

```
yuqing/
├─ server/          FastAPI 网关（自有 API + dsh 桥）
├─ plugins/         dsh 插件（舆情工具：hotlist/heat_state/evidence/chain.write）
├─ mcp/             Python MCP server（五表只读、采集调度——Python 存量入口）
├─ teams/           agent-teams profile（六角色+门禁定义）
├─ frontend/        Vue3 控制台（原型 → 组件化）
├─ scripts/         heat_state.py 等已验证脚本
└─ docs/            本规划 + 原型 + 讲解稿
```
